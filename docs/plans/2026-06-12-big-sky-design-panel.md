# ClaudeOS Big-Sky Design Panel — Full Report

*Generated 2026-06-12 by a 3-lens multi-agent design panel (6 agents). Every factual claim was checked by verifier agents against the flake's locked nixpkgs (`nix eval`), upstream sources, and the Claude Code docs. Verdicts: ✅ confirmed · 🟡 partially · ❌ refuted · ❔ unverifiable from this machine.*

**Brief:** (1) modernize the stack (PipeWire-vs-ALSA-class swaps, oxidized userland) and find novel chains of technologies that serve a real purpose; (2) make Claude intertwined with system tools beyond what a bash script enables — running on the Claude Max subscription only, no API spend, no Fable dependency.

## Lens 1 — Kernel / systemd / low-level modernization

### sched_ext interactivity: scx_lavd with power-aware mode switching
*Type: drop-in-modernization*

**Pitch.** Replace the kernel's default EEVDF scheduling policy with the scx_lavd BPF scheduler, which was built for latency-critical interactive workloads on battery-powered devices (Steam Deck lineage). On a Niri desktop this is felt as: compositor and audio stay smooth while a nixos-rebuild or cargo build saturates all cores of the XPS 13's 4-core i7-8550U. Both laptops already run linuxPackages_latest, so sched_ext is available with zero kernel work.

**Wiring.** services.scx.enable = true; services.scx.scheduler = "scx_lavd"; (verified present in this flake's nixpkgs — the scheduler enum includes scx_lavd). services.scx.extraArgs (verified, list of string) can pass ["--autopower"] so lavd flips between performance/powersave modes based on AC state. Add to modules/common/ or a new modules/common/scheduler.nix via the add-module pattern; enable on transporter first per the testbed convention. Rollback is trivial: stopping the scx systemd service falls back to EEVDF instantly, which is exactly why this is a safe bleeding-edge toy.

**Wow vs. toil.** Felt daily if the laptop ever stutters under load; invisible if it doesn't. Toil is near-zero (one module, instant fallback to EEVDF if the userspace daemon dies — the kernel guarantees this). The honest risk is that on a 4-core U-series chip the win over EEVDF is modest; transporter A/B testing under a kernel-build workload settles it in an afternoon.

### Perlless immutable core: userborn + system.etc.overlay + sysusers
*Type: drop-in-modernization*

**Pitch.** Swap the 20-year-old Perl activation machinery for the modern Rust/systemd path: userborn manages users from a declarative manifest, /etc becomes an overlayfs composed at boot by systemd-initrd instead of being assembled by activation scripts. This is the direction NixOS itself is heading (the perlless profile), and this repo is unusually well-positioned: boot.initrd.systemd.enable is already true in modules/common/boot.nix, which is the hard prerequisite.

**Wiring.** services.userborn.enable = true; system.etc.overlay.enable = true; system.etc.overlay.mutable = true; (all three verified present via nix eval). Start with mutable=true so anything that writes /etc keeps working; graduate to immutable later. Optionally import nixos/modules/profiles/perlless.nix to enforce no-Perl in the closure. Watch two repo-specific interactions: sops-nix secret templating into /etc, and the system.activationScripts.snapperSubvolumes + /bin/bash scripts in modules/common/system.nix — activation scripts still run with etc.overlay, but verify ordering. Deploy to transporter first; this touches early boot, and snapper pre/post snapshots plus systemd-boot generations give two independent rollback paths.

**Wow vs. toil.** Felt at every boot (faster, no Perl in the hot path) and every rebuild (activation gets simpler and more atomic), plus bragging rights of a perlless NixOS. Toil is front-loaded: one weekend of transporter shakedown for sops-nix and stray /etc writers, then essentially zero. The immutable-/etc endgame is real hardening, not cosmetics.

### envfs: delete the /bin/bash activation hack
*Type: drop-in-modernization*

**Pitch.** modules/common/system.nix:82-85 hand-symlinks /bin/bash via an activation script because Claude Code plugin hooks assume it exists. envfs replaces that point-fix with a FUSE filesystem on /bin and /usr/bin that resolves ANY interpreter from the calling process's PATH — so the next third-party script that wants /usr/bin/python or /bin/zsh also just works, instead of generating another activation hack.

**Wiring.** services.envfs.enable = true; (verified present) and delete the system.activationScripts text block at modules/common/system.nix:82-85 in the same commit — a leftover real symlink in /bin can conflict with the mount point. envfs is by the nix-community/Mic92 lineage and is the canonical NixOS answer to exactly this problem. Note envfs guarantees /bin/sh and /usr/bin/env as static fallbacks even when the resolver has no PATH match.

**Wow vs. toil.** Small but genuinely felt: a whole class of "works on Ubuntu, breaks on NixOS" script failures disappears, which matters in a repo whose whole point is running third-party Claude tooling. Toil: one more FUSE daemon in the TCB; if it wedges, scripts relying on it fail until restart. Net positive — it deletes bespoke code and replaces it with a maintained community component.

### Rust ring 2: sudo-rs + uutils coreutils + dbus-broker
*Type: drop-in-modernization*

**Pitch.** Extend the existing oxidized userland (fish 4, eza/fd/ripgrep/etc.) one layer down: memory-safe sudo, Rust coreutils on the user PATH, and dbus-broker replacing the reference dbus daemon. sudo-rs is what Ubuntu now ships by default; dbus-broker is the Fedora/Arch default and measurably faster for desktop IPC bursts (relevant under Niri+Noctalia which are chatty over the bus).

**Wiring.** security.sudo-rs.enable = true; security.sudo.enable = false; — sudo-rs honors wheel and the existing security.sudo.wheelNeedsPassword pattern at modules/common/users.nix:34 maps to security.sudo-rs.wheelNeedsPassword. services.dbus.implementation = "broker"; (verified: enum dbus|broker). For coreutils, do NOT try to swap the stdenv (mass rebuild, unsupported); instead add pkgs.uutils-coreutils-noprefix (verified: uutils-coreutils-0.9.0) to home.packages with lib.hiPrio so it wins on the interactive PATH while system scripts keep GNU coreutils — the two-ring philosophy applied to coreutils.

**Wow vs. toil.** sudo-rs and dbus-broker are felt as nothing happening — which for security plumbing is success — plus a faster bus under notification storms. uutils on the user PATH is the risky third: ~GNU-compatible but date/stat edge cases still bite scripts; keeping it user-ring-only contains the blast radius. Low toil overall; each piece reverts independently.

### Time-machine desktop: Claude-labeled generations + annotated snapshots + soft-reboot
*Type: novel-chain*

**Pitch.** Today both systemd-boot entries and snapper pre/post pairs are anonymous numbers; rolling back means archaeology. Chain three things: the weekly auto-update agent (which already reads the flake.lock diff) writes a one-line human summary that becomes the generation's boot-menu label AND the snapper snapshot description; a rebuild wrapper then offers `systemctl soft-reboot` to enter the new userspace in ~5 seconds when the kernel didn't change. Result: the boot menu reads like a changelog ('niri 25.05→25.08, kernel held'), every snapshot says what it guards, and switching generations feels like switching browser tabs. This is the OS-is-a-git-repo leverage: the agent that makes the change is the one that documents it in the bootloader.

**Wiring.** Three legs. (1) Labels: system.nixos.label (verified, string option) is set from a file the auto-update agent writes (e.g. environment variable NIXOS_LABEL or builtins.readFile ./generation-label.txt committed alongside flake.lock) — systemd-boot entries render it. (2) Snapshots: extend the existing rebuild flow in modules/common/snapshots.nix to run `snapper modify -d "$label" $POST_NUM` after switch; the description text is the same Claude-authored line. (3) Soft-reboot: a fish function around the existing rebuild abbreviation — after nixos-rebuild switch, compare /run/current-system/kernel with /run/booted-system/kernel; if identical, offer `systemctl soft-reboot` to cleanly restart all of userspace (greetd, Niri, pipewire) into the new generation without firmware/POST. Explicitly evaluated and REJECTED: bcachefs as the snapshot substrate — it was dropped from the mainline kernel (externally maintained DKMS since ~6.17), which on a linuxPackages_latest flake means recurring breakage against years of working btrfs+snapper investment; not worth it even for this user.

**Cost profile.** Claude work piggybacks on the existing weekly auto-update agent run (sonnet-class, already budgeted); manual rebuilds optionally call `claude -p` with haiku once per rebuild (~daily at most) to summarize the git diff into a label. Soft-reboot/snapper legs are zero-cost.

**Wow vs. toil.** This is the highest felt-value idea: every interaction with the boot menu, `snapper list`, and post-rebuild restart gets better, and it converts existing Claude output (the weekly review) into durable OS artifacts instead of a text file. Toil: the soft-reboot leg is genuinely experimental on NixOS and needs a transporter shakedown; the label/annotation legs are robust and worth doing even if soft-reboot is deferred.

### BPF flight recorder: below + oomd/unit-failure journal triggers feeding claude-monitor
*Type: claude-integration*

**Pitch.** claude-monitor Tier 2 currently hands Claude a thin alert-context file; Claude narrates symptoms without evidence. Chain below (Meta's BPF-based cgroup history recorder, like atop-but-structured) so that when systemd-oomd kills something or a unit hits OnFailure, the notifier extracts the minutes-before-incident cgroup timeline and hands it to haiku — the notification then names the actual culprit and its growth curve ('codium renderer grew 1.2G→5.8G in 90s before oomd acted; likely the X extension; run Y'). That is forensics a bash script cannot author, and it makes the existing zram+oomd stack legible.

**Wiring.** services.below.enable = true; (verified) runs the below daemon recording to /var/log/below continuously at negligible overhead. Trigger side: a systemd user/system service running `journalctl -f -u systemd-oomd -o json` (or match on systemd-oomd's kill MESSAGE_ID) that, on event, runs `below dump system --begin '5 min ago' --json` plus `below dump process ...`, prepends it to the existing alert-context file in modules/apps/claude-monitor, and invokes the existing rate-limited notify path with --model haiku. Same pattern hooks the existing health-check Tier 1: when it flags an anomaly, it attaches below history instead of instantaneous `ps` output. Optionally drop pkgs.bpftrace into systemPackages so interactive Claude sessions (the system-health MCP server) can run one-liner probes when the user asks 'why is the fan on'.

**Cost profile.** haiku, strictly event-driven (oomd kills, unit failures — realistically a few times a week), reusing claude-monitor's existing 30-minute cooldown; the recorder itself is free. Zero scheduled Claude calls added.

**Wow vs. toil.** Felt exactly when something dies — which is when the user most wants magic — and it upgrades an existing skeleton rather than adding a new service. Toil: below is a stable Meta project but its CLI flags need pinning in the script; the journal-watcher unit is ~30 lines. Honest caveat: on a well-behaved system events are rare, so weeks may pass without seeing it work.

### Confined autonomy: systemd + Landlock sandbox ring for the agents that edit the OS
*Type: novel-chain*

**Pitch.** The weekly auto-update agent and claude-monitor run Claude with commit rights to the repository that IS the operating system, as plain user processes that could touch all of $HOME. Build the confinement story that makes scaling autonomy safe: the agent units get kernel-enforced boundaries (mount-namespace allowlists plus Landlock/BPF-LSM), so 'the OS fixes itself' can be granted broader powers — auto-merging its own PRs on transporter, say — because a bad tool call physically cannot write outside ~/.config/claudeos and its state dirs. Sandboxing is the prerequisite for the next level of agency, not a gimmick.

**Wiring.** Layer 1 (solid, namespace-based): harden systemd.user.services.claudeos-auto-update and the claude-monitor units in-place with serviceConfig: ProtectHome=tmpfs, BindPaths= the repo + ~/.claude + ~/.local/bin/claude + XDG cache dirs, ProtectSystem=strict, NoNewPrivileges=true, PrivateTmp=true. Layer 2 (Landlock, path-granular without namespaces): wrap the claude invocation in landrun or Anthropic's open-source sandbox-runtime (srt), which apply Landlock rulesets; requires "landlock" in the kernel's lsm= list (check /sys/kernel/security/lsm — NixOS default kernels enable Landlock; add boot.kernelParams lsm= override only if missing). Layer 3 (BPF-LSM): systemd RestrictFileSystems= on the units to pin allowed fs types — needs CONFIG_BPF_LSM active. The transporter/gti split maps naturally: looser ring on the testbed, strict on the daily driver.

**Cost profile.** n/a — no Claude calls added; it constrains existing ones. Indirectly enables cheaper autonomy later (more agent runs become acceptable once confined).

**Wow vs. toil.** Not felt daily — felt the one time it matters, and felt immediately as confidence to let the weekly agent do more (the actual payoff). Toil is real: sandbox-vs-Claude-Code friction (credential paths, the self-updater, MCP server sockets) takes iteration, and Landlock tooling availability in nixpkgs is the weakest verified link. Do Layer 1 now (pure systemd, an hour of work), treat Layers 2-3 as the experiment they are.

## Lens 2 — Nix-ecosystem superpowers

### VM boot smoke-test gate for the weekly auto-update
*Type: novel-chain*

**Pitch.** Right now auto-update.nix (line 64) only checks that the new generation *builds*; a generation can build fine and still boot into a broken session. Add a gate that boots the freshly-built generation in a throwaway QEMU VM, waits for multi-user.target and greetd.service, and asserts zero failed systemd units — only then commit/push/switch. This is the thing only NixOS can do: the entire next OS state is a derivation you can boot headlessly before betting your laptop on it.

**Wiring.** Cleanest mechanism: the NixOS test framework. Add a flake check `checks.x86_64-linux.boot-smoke = pkgs.testers.runNixOSTest { node imports the host's module list; testScript = ''machine.wait_for_unit("multi-user.target"); machine.wait_for_unit("greetd.service"); machine.succeed("systemctl is-system-running --wait | grep -Ev degraded")''; }`. The auto-update script in modules/common/auto-update.nix gains one step between the toplevel build and the commit: `nix build .#checks.x86_64-64.boot-smoke` (KVM required — both Dell laptops have it; gate on /dev/kvm). Lighter alternative: `nix build .#nixosConfigurations.$HOST.config.system.build.vm` (exists for every NixOS config; tune RAM via `virtualisation.vmVariant.virtualisation.memorySize`) and drive it with a serial-console expect script — but runNixOSTest gives you the python driver (wait_for_unit, succeed) for free. microvm.nix (github:astro/microvm.nix) is overkill here: it shines for persistent service VMs, not one-shot smoke tests. Claude chain on failure: feed the test driver log + `nix store diff-closures` to a full `claude` agent session in the repo with the instruction 'bisect flake inputs: re-pin one input at a time to the old rev, rebuild the smoke test, find the culprit, open a branch pinning it with a comment'. That produces a PR-shaped artifact, not a notification.

**Cost profile.** Weekly, inside the existing Sat 03:00 timer. Zero Claude cost on the happy path; sonnet/opus agent session only when the smoke test fails (rare). VM boot adds ~1-3 min and ~2 GB RAM during the run.

**Wow vs. toil.** High wow the first time a bad update gets caught before touching the real system — turns autoApply=true from reckless to reasonable, which is the real unlock. Toil: writing the test node so it imports the host config without hardware-configuration.nix conflicts (filesystems/disko must be overridden in the VM variant) is a half-day of fiddling; after that it is maintenance-free.

### lanzaboote: Secure Boot with self-signed UKIs
*Type: drop-in-modernization*

**Pitch.** Sign every generation as a Unified Kernel Image with your own keys and enroll them in the Dell firmware, closing the unsigned-bootloader hole and pairing naturally with the existing systemd-boot + systemd-initrd + Plymouth stack (lanzaboote replaces systemd-boot's stub but keeps the same menu UX). Honest caveat found in the repo: disko.nix shows no LUKS, so the marquee payoff — TPM2-backed auto-unlock via systemd-cryptenroll — does not apply today; without disk encryption this is boot-chain integrity only.

**Wiring.** Flake input `lanzaboote.url = "github:nix-community/lanzaboote"` (use a release tag, e.g. v0.4.x), import `lanzaboote.nixosModules.lanzaboote`, set `boot.lanzaboote.enable = true; boot.lanzaboote.pkiBundle = "/var/lib/sbctl";` and `boot.loader.systemd-boot.enable = lib.mkForce false;` in modules/common/boot.nix. One-time imperative steps per host: `sbctl create-keys`, reboot into firmware Setup Mode (Dell BIOS: clear Secure Boot keys / 'Audit Mode'), `sbctl enroll-keys --microsoft`, enable Secure Boot. Verify with `bootctl status`. Note boot.loader.systemd-boot.configurationLimit (currently 5) maps to `boot.lanzaboote.configurationLimit`.

**Cost profile.** n/a — no Claude involvement.

**Wow vs. toil.** Wow is one-time (green `bootctl status`, bootkit resistance, the bragging right of self-signed UKIs); daily-felt value near zero without LUKS. Toil: one risky afternoon per machine (key enrollment can soft-brick boot until you disable SB in firmware — always recoverable on these Dells), then fully declarative. Recommend doing transporter (testbed) first; consider bundling with a future LUKS+TPM2 migration where the payoff becomes daily.

### nh + nix-output-monitor + nvd: rebuild UX overhaul
*Type: drop-in-modernization*

**Pitch.** Replace the raw nixos-rebuild internals of the hand-rolled fish `rebuild` function (home/shell/fish.nix:126) with `nh os switch`: live build-graph visualization (nom), an automatic closure diff (nvd) showing exactly what changed, and a confirmation prompt before activation. Also takes over garbage collection declaratively, replacing ad-hoc gc with a policy.

**Wiring.** NixOS options exist in nixpkgs: `programs.nh.enable = true; programs.nh.flake = "/home/tom/.config/claudeos"; programs.nh.clean.enable = true; programs.nh.clean.extraArgs = "--keep 5 --keep-since 14d";` (clean ships a systemd timer; disable any existing nix.gc.automatic to avoid double-gc). Keep the fish `rebuild` wrapper but gut its middle: snapper pre-snapshot → `nh os switch` (no path needed, NH_FLAKE/programs.nh.flake supplies it) → snapper post-snapshot. nvd diff output is printed by nh automatically; optionally pipe it to the existing haiku changelog habit. Add `nvd` and `nix-output-monitor` to environment.systemPackages for standalone use (`nvd diff /run/current-system ./result`).

**Cost profile.** n/a — no Claude involvement.

**Wow vs. toil.** Felt on every single rebuild — this is the highest wow-per-effort item on the list; the nvd diff also makes the snapper snapshot descriptions meaningful. Toil: ~30 minutes, minus risk that nh's prompt behavior needs --no-confirm inside the auto-update service. Deletes ~40 lines of bespoke fish.

### nix-index-database + comma: trace-free 'run anything'
*Type: drop-in-modernization*

## Lens 3 — Claude woven into the OS (agentic architecture)

### Self-Healing Units: OnFailure → Claude agent → fix PR (claude-heal@.service)
*Type: claude-integration*

**Pitch.** A systemd template unit `claude-heal@.service` attached via `unitConfig.OnFailure = ["claude-heal@%n.service"]` to opted-in units. When a unit fails, a headless Claude Code agent session gets the unit's journal, `systemctl show` output, and the owning module file in the claudeos repo, then creates a branch, edits the Nix module, validates with `nix build --dry-run`, and opens a PR with `gh pr create`. The OS literally files its own fix PRs — irreproducible with a bash script because the agent must read the module, reason about the failure, and produce a reviewed artifact.

**Wiring.** New `modules/common/self-heal.nix` exposing `claude-os.selfHeal.units = [ ... ]` that maps to `systemd.services.<name>.unitConfig.OnFailure = [ "claude-heal@%n.service" ]` (user units mirror via `systemd.user.services`). The template's ExecStart script: rate-limit via flock + cooldown file in $XDG_CACHE_HOME (reuse the claude-monitor cooldown pattern at /home/tom/Projects/claudeos/modules/apps/claude-monitor/default.nix), gather `journalctl -u $1 -n 300 --no-pager` + `grep -rn` the repo for the unit name, then run `claude -p --model sonnet --allowedTools 'Read,Grep,Glob,Edit,Bash(git *),Bash(gh pr create*),Bash(nix build*),Bash(journalctl*),Bash(systemctl status*)'` with a prompt mandating: work on a branch named heal/<unit>-<date>, never touch main, validate with `nix build .#nixosConfigurations.$(hostname)... --dry-run`, open PR, send Telegram/notify-send with the PR URL. Never attach OnFailure to claude-heal@ itself or to claudeos-health-check (loop prevention). Packages: gh (already common), nix, git.

**Cost profile.** Event-driven, rare (only on unit failure, flock + 1h cooldown). Sonnet for the agent session. Zero idle cost; covered by Max subscription.

**Wow vs. toil.** Highest wow of the set: waking up to a PR titled 'fix: claudeos-auto-update failed on stale git stash' is the flagship demo. Toil: prompt needs tuning so the agent doesn't propose silly fixes for transient failures (network blips) — mitigate by having the agent first classify transient-vs-config and exit early for transient. PRs are reviewed, so hallucinated fixes cost only review time, not system breakage.

### Self-Narrating Boot Menu (two-phase label injection)
*Type: claude-integration*

**Pitch.** Every rebuild, Haiku writes a one-line slug from the nvd closure diff into `system.nixos.label`, so the systemd-boot menu reads like a changelog ('niri-bump_fixed-idle-lock' instead of 'Generation 213'). Critique of the seed: the label is baked at eval time, so a post-build sed of /boot/loader/entries is fragile (switch-to-configuration regenerates all entries on every bootloader install). The robust mechanism is two-phase: build → diff → label file → switch, with the label read from a repo-tracked file.

**Wiring.** Extend the existing `rebuild` fish function in /home/tom/Projects/claudeos/home/shell/fish.nix: (1) `nix build .#nixosConfigurations.(hostname)...toplevel`, (2) `nvd diff /run/current-system ./result` (add pkgs.nvd), (3) `claude -p --model haiku 'compress this closure diff into <=40 chars, only [a-zA-Z0-9:_.-], hyphen-separated'`, (4) sanitize with `string replace -ra '[^a-zA-Z0-9:_.-]' '-'` and write to `hosts/(hostname)/boot-label.txt`, (5) in modules/common/system.nix set `system.nixos.label = lib.mkIf (builtins.pathExists labelFile) (lib.fileContents labelFile)`, (6) git add + `nixos-rebuild switch`. **Cost profile.** One Haiku call per rebuild (a few times/week). Negligible.

**Wow vs. toil.** Daily-felt: every boot menu and `nixos-rebuild list-generations` becomes self-documenting, and it pairs with snapshot archaeology for rollbacks ('boot the generation labeled before-pipewire-bump'). Toil: low once the sanitizer is right; failure mode is a useless label, which falls back to the date — never breaks the build if mkIf/fallback is in place.

### Hook-Enforced Repo Guardrails (the repo defends itself)
*Type: claude-integration*

### Journald Diary: error triage with persistent memory
*Type: claude-integration*

**Pitch.** A nightly Haiku pass over `journalctl -p err..alert --since yesterday` that dedups against a Claude-maintained known-issues ledger (docs/known-issues.md in the repo). New error signatures get triaged; recurring config-rooted ones escalate to the self-heal agent (idea 1) to open a PR. Unlike a grep cron job, the agent maintains its own memory across runs — it knows 'this bluetooth warning is benign, noted 2026-05-12' — and its memory file is itself a reviewable git artifact.

**Wiring.** systemd user timer `claudeos-journal-diary` (OnCalendar=daily 04:00) in modules/apps/claude-monitor: script pipes deduped `journalctl --output=cat -p err --since -1d | sort | uniq -c | sort -rn | head -50` into `claude -p --model haiku --allowedTools 'Read,Edit(docs/known-issues.md),Bash(journalctl*)'` with instructions: compare against docs/known-issues.md, append new entries with date+verdict (benign/watch/actionable), output only actionable items. Actionable output lands in the existing daily-brief cache file (modules/apps/claude-monitor writes $CACHE_DIR/daily-brief.txt) so it surfaces in the 9 AM brief and first-shell MOTD. Ledger changes are committed on the next auto-update run, or by the agent itself with the idea-4 git allowlist.

**Cost profile.** One Haiku (or Sonnet) call per night, bounded input (top 50 deduped lines). Trivial under Max.

**Wow vs. toil.** Felt in the morning brief: 'one new error signature last night: sops-nix key warning on transporter — likely from Tuesday's secrets change, see ledger' is operator-grade awareness no notification pipe gives. Toil: low-moderate; the ledger needs a strict format in the prompt or it drifts. Failure mode is benign: a noisy ledger, fixed by editing one markdown file.

## Synthesis (as discussed in session)

**Thesis:** NixOS is the only OS where the entire system is one git repo, so "the OS maintains itself" reduces to "an agent edits a repo and opens a PR." Every Claude feature below is event-driven/scheduled on the Max subscription — haiku for high-frequency paths, sonnet-class only for rare agentic work. Nothing requires Fable to run.

**Approved build order:** (A) Quick wins + time-machine chain — envfs, nix-index-database+comma, nh+nom, sudo-rs, dbus-broker, uutils@hiPrio, scx_lavd, Claude-labeled generations + annotated snapshots. (B) Flagship self-maintaining OS — self-heal OnFailure agents, journald diary with persistent ledger, bidirectional Telegram ops (inbound routing confirmed supported by the plugin), hook-enforced constitution. Parked: VM smoke-test gate, compositor specialisations, lanzaboote, userborn/etc-overlay (testbed-first tier), impermanence (testbed-only verdict).
